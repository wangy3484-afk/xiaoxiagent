# Spec Delta

## Purpose

本能力用于在报告交付前执行独立、可解释的专业质量审查，识别证据、逻辑、适配性、可执行性和衡量设计上的缺陷，防止将表面完整但不可用的内容交付给运营人员。

## ADDED Requirements

### Requirement: 按专业维度评估报告质量

系统 MUST 从需求完整性、证据质量、场景适配性、策略逻辑、执行可行性、指标可衡量性和风险覆盖七个维度审查报告，并为每个维度给出结论、依据和需要修正的问题。

#### Scenario: 报告进入交付前审查
- **WHEN** 系统完成报告初稿
- **THEN** 系统对七个质量维度分别进行评估
- **AND** 生成可查看的质量审查摘要

### Requirement: 设置不可绕过的交付阻断项

系统 MUST 将以下情况视为交付阻断项：核心目标或目标用户不明确、关键事实无法追溯来源、核心策略没有场景适配说明、执行计划缺少时间或验收方式、指标没有口径或验证方法、已知重大风险未处理。存在阻断项的报告不得标记为正式完成。

#### Scenario: 关键事实缺少来源
- **WHEN** 报告以确定语气引用了无法追溯的外部事实或数据
- **THEN** 质量审查标记交付阻断
- **AND** 要求补充证据、降级为假设或删除该主张

#### Scenario: 方案缺少执行闭环
- **WHEN** 核心策略没有对应的行动、时间节点、指标或验收方式
- **THEN** 质量审查标记交付阻断
- **AND** 报告不得进入正式完成状态

### Requirement: 检查主张与证据的一致性

系统 MUST 检查证据是否真正支持报告中的主张，避免把相关性描述为因果关系、把单一案例描述为普遍规律，或把企业宣传内容直接当作效果证明。

#### Scenario: 来源只证明实施动作
- **WHEN** 来源只能证明某企业实施过一项运营动作但没有效果数据
- **THEN** 系统可以陈述实施事实
- **AND** 不得声称该动作已经被证明带来特定业务提升

#### Scenario: 单一案例被用于支持普遍结论
- **WHEN** 报告根据一个案例得出普遍适用的结论
- **THEN** 质量审查要求缩小结论范围
- **AND** 将其标记为需要在当前场景验证的假设

### Requirement: 检查方案内部一致性

系统 SHALL 检查运营目标、用户分层、策略、行动、资源、时间表和指标之间是否一致。发现相互冲突或无法同时满足的要求时，报告 MUST 说明取舍，不得静默保留冲突。

#### Scenario: 目标与资源不匹配
- **WHEN** 报告目标所需资源明显超过用户确认的预算或周期
- **THEN** 质量审查标记冲突
- **AND** 要求降低范围、调整目标或明确新增资源需求

#### Scenario: 指标无法验证策略目标
- **WHEN** 计划中的指标不能反映核心策略是否有效
- **THEN** 质量审查要求补充或替换指标

### Requirement: 防止虚假精确和隐性假设

系统 MUST 识别缺乏依据的精确数字、效果承诺和默认前提，并将其删除、改为区间或明确标记为假设。所有会显著影响策略成立的假设 SHALL 在报告中集中列出。

#### Scenario: 缺少基线却给出精确提升目标
- **WHEN** 报告在没有业务基线或证据的情况下给出精确提升比例
- **THEN** 质量审查不得通过该内容
- **AND** 要求改为待验证区间或实验目标

#### Scenario: 策略依赖未确认能力
- **WHEN** 策略依赖用户尚未确认的数据、渠道或团队能力
- **THEN** 报告将该依赖列为关键假设和执行前置条件

### Requirement: 披露无法解决的质量限制

如果由于公开证据不足、用户信息缺失或外部服务失败而无法满足某项质量要求，系统 MUST 向用户明确说明限制、受影响的报告部分和建议的补救措施，不得以完整正式报告掩盖缺口。

#### Scenario: 证据不足但仍可提供方向性建议
- **WHEN** 缺少足够案例证据但现有信息允许提供初步方向
- **THEN** 系统将输出标记为方向性草案而非正式报告
- **AND** 说明需要补充的证据或验证步骤

#### Scenario: 关键输入始终无法获得
- **WHEN** 用户无法提供影响策略选择的关键输入
- **THEN** 系统说明哪些结论因此无法确定
- **AND** 给出多个条件化方案而不是选择未经支持的单一方案
