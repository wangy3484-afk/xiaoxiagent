# Spec Delta

## Purpose

本能力用于把运营人员的自然语言想法转化为完整、可确认、可用于专业研究的运营简报，避免系统在目标、用户、资源或基线不清楚时直接生成泛化方案。

## ADDED Requirements

### Requirement: 接收并结构化运营场景

系统 SHALL 接收运营人员使用自然语言描述的业务场景，并提取业务背景、当前问题、运营目标、目标用户、业务阶段、执行周期、预算与资源、已有渠道、当前基线和限制条件。系统 MUST 将无法从输入中确认的字段标记为未知，不得自行补造为已知事实。

#### Scenario: 输入包含完整运营信息
- **WHEN** 用户提交了业务背景、目标、用户、周期、资源和现状数据
- **THEN** 系统生成包含全部已识别字段的结构化运营简报
- **AND** 每个字段能够追溯到用户输入

#### Scenario: 输入为非结构化想法
- **WHEN** 用户只用一段自然语言描述运营想法
- **THEN** 系统提取能够确认的信息
- **AND** 将缺失信息明确标记为未知
- **AND** 不把推测内容记录为用户提供的事实

### Requirement: 识别主要及辅助运营场景

系统 SHALL 从拉新增长、用户留存、活动运营和内容运营中识别一个主要场景，并在适用时识别一个或多个辅助场景。系统 SHALL 给出分类依据，并允许用户修正分类结果。

#### Scenario: 单一运营场景
- **WHEN** 用户目标明确属于一种运营类型
- **THEN** 系统将其标记为主要运营场景
- **AND** 展示用于分类的目标和问题依据

#### Scenario: 跨场景需求
- **WHEN** 用户需求同时涉及多种运营类型
- **THEN** 系统根据核心目标确定主要场景
- **AND** 将其他相关类型标记为辅助场景
- **AND** 向用户解释主次关系

### Requirement: 根据场景进行专业澄清

系统 MUST 在信息不足时根据主要运营场景生成有优先级的澄清问题。至少应核验目标、目标用户、当前问题、执行周期、资源限制和可用基线；不同运营场景还 SHALL 使用对应的专项问题补齐分析所需信息。

#### Scenario: 缺少生成专业方案所需信息
- **WHEN** 结构化运营简报缺少必需信息
- **THEN** 系统暂停进入正式研究与报告生成
- **AND** 提出能够直接补齐关键缺口的澄清问题

#### Scenario: 用户无法提供基线数据
- **WHEN** 用户确认当前没有某项基线数据
- **THEN** 系统将该字段记录为未知
- **AND** 后续报告必须将相关目标或测算标记为待验证假设

### Requirement: 用户确认运营简报

系统 MUST 在开展正式案例研究前向用户展示结构化运营简报，并允许用户修改或确认。未经确认的内容不得被当作最终需求依据。

#### Scenario: 用户修改系统提取结果
- **WHEN** 用户发现运营简报中的分类或字段不准确并进行修改
- **THEN** 系统保存修改后的内容
- **AND** 使用修改后的版本开展后续研究

#### Scenario: 用户确认运营简报
- **WHEN** 用户确认结构化运营简报
- **THEN** 系统将其作为本次报告的需求基线
- **AND** 后续报告能够引用该基线中的目标与约束

### Requirement: 明确输入数据边界

系统 SHALL 在场景录入处明确提示本产品不需要个人身份信息、客户明细或公司机密数据，并允许用户仅使用汇总信息和非敏感业务描述完成需求输入。

#### Scenario: 用户准备提交运营场景
- **WHEN** 用户进入场景录入流程
- **THEN** 系统展示不得输入个人隐私和公司机密信息的提示
- **AND** 说明可以使用汇总指标、区间或匿名描述替代敏感数据
