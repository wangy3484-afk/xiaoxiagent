# Spec Delta

## Purpose

本能力用于将经过核验的案例机制与用户的实际业务目标、资源和限制相结合，形成覆盖诊断、策略、执行、指标、实验和风险的专业运营方案，而非通用建议列表。

## ADDED Requirements

### Requirement: 形成运营问题诊断

系统 MUST 在提出策略前说明当前业务阶段、目标用户、关键行为路径、核心问题、主要约束和优先级，并建立从业务目标到运营目标再到观测指标的目标关系。

#### Scenario: 用户提出结果型目标
- **WHEN** 用户只提出提升增长、留存、活跃或转化等结果型目标
- **THEN** 系统将结果型目标拆解为可干预的用户行为和运营环节
- **AND** 说明最值得优先解决的核心问题及判断依据

#### Scenario: 诊断依赖缺失数据
- **WHEN** 核心问题无法由现有信息确定
- **THEN** 系统列出多个可能解释
- **AND** 指出区分这些解释所需补充的数据或实验

### Requirement: 应用场景专项运营方法

系统 SHALL 根据主要运营场景应用相应的专项分析框架，并允许辅助场景补充方案。专项分析 MUST 形成该场景特有的关键决策，不得仅替换标题或术语。

#### Scenario: 拉新增长方案
- **WHEN** 主要场景为拉新增长
- **THEN** 报告覆盖目标人群、价值主张、渠道组合、触达路径、转化漏斗、获客成本假设和渠道验证方案

#### Scenario: 用户留存方案
- **WHEN** 主要场景为用户留存
- **THEN** 报告覆盖用户生命周期、关键留存行为、分层、流失信号、触发机制、召回策略和分群验证方案

#### Scenario: 活动运营方案
- **WHEN** 主要场景为活动运营
- **THEN** 报告覆盖活动目标、目标人群、核心机制、利益设计、传播节奏、执行资源、异常预案和复盘设计

#### Scenario: 内容运营方案
- **WHEN** 主要场景为内容运营
- **THEN** 报告覆盖内容定位、目标受众、主题矩阵、内容供给、生产节奏、分发渠道、互动机制和转化路径

### Requirement: 将案例机制适配到当前场景

系统 MUST 对每项核心策略说明其参考证据、适用前提、与当前场景的差异、需要进行的调整以及预期影响路径。系统不得把头部企业案例直接表述为适用于当前用户的结论。

#### Scenario: 采用案例中的运营机制
- **WHEN** 报告建议借鉴某个案例机制
- **THEN** 报告说明该机制解决的问题和生效条件
- **AND** 说明针对用户资源、渠道和业务阶段所做的调整

#### Scenario: 案例不具备直接迁移条件
- **WHEN** 某案例依赖当前用户不具备的品牌、流量、数据或组织能力
- **THEN** 系统不得建议直接复制完整做法
- **AND** 提供可验证的缩小版本或放弃采用的理由

### Requirement: 提供可执行的阶段计划

系统 SHALL 根据用户设定的周期生成分阶段执行计划；未指定周期时，默认提供 30/60/90 天计划。每项行动 MUST 包含目标、目标人群、行动内容、渠道或触点、建议负责人角色、前置条件、所需资源、交付物、时间节点和验收方式。

#### Scenario: 用户未指定执行周期
- **WHEN** 已完成策略设计但用户没有指定周期
- **THEN** 系统生成 30/60/90 天分阶段计划
- **AND** 将早期阶段用于验证关键假设

#### Scenario: 用户指定短期活动周期
- **WHEN** 用户给出明确的活动开始和结束时间
- **THEN** 系统按照预热、上线、持续运营、收尾和复盘阶段安排任务
- **AND** 每个阶段包含可观察的交付物和验收方式

### Requirement: 设计可衡量的指标和实验

系统 MUST 为核心策略定义结果指标、过程指标和风险指标，并说明指标口径、计算方式、数据来源、观测周期和判断规则。对于未被证据支持的提升幅度或目标值，系统 MUST 标记为待验证假设，并提供验证实验。

#### Scenario: 存在可靠业务基线
- **WHEN** 用户提供了可靠的当前基线
- **THEN** 系统基于基线提出目标区间及其依据
- **AND** 给出对应的观测周期和判断规则

#### Scenario: 不存在可靠业务基线
- **WHEN** 用户没有提供可用基线
- **THEN** 系统不得给出伪精确的效果承诺
- **AND** 设计用于建立基线或验证目标区间的最小实验

### Requirement: 明确资源、预算与风险假设

系统 SHALL 汇总方案所需人员角色、渠道、工具、内容产能、时间和预算假设。无法获得准确价格或工作量时，系统 MUST 使用区间、计算方法或待确认项表达，不得将估算值描述为事实。

#### Scenario: 用户提供预算上限
- **WHEN** 用户提供明确预算上限
- **THEN** 系统对策略进行优先级排序并控制建议范围
- **AND** 标明不可在当前预算内同时完成的内容

#### Scenario: 用户未提供预算
- **WHEN** 用户未提供预算信息
- **THEN** 系统列出预算构成和测算方法
- **AND** 将具体金额标记为待用户确认

### Requirement: 输出完整的专业运营报告

系统 SHALL 输出包含执行摘要、运营简报、问题诊断、目标与指标、用户分析、案例证据、策略设计、执行计划、资源与预算、实验方案、风险预案和证据附录的报告。报告 MUST 明确区分事实、推断、建议和假设。

#### Scenario: 生成正式报告
- **WHEN** 运营简报、证据研究、策略设计和质量检查均满足交付条件
- **THEN** 系统按照统一结构生成完整运营报告
- **AND** 每项关键策略能够追溯到需求依据、案例证据或明确标记的专业推断

### Requirement: 保持决策支持边界

系统 SHALL 将输出定位为运营决策支持，不得代表用户自动创建、投放、发布或修改任何外部运营活动。

#### Scenario: 报告包含可执行动作
- **WHEN** 系统生成渠道投放、内容发布或活动执行建议
- **THEN** 系统仅输出计划和操作说明
- **AND** 不调用外部平台执行这些动作
