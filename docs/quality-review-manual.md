# 运营报告质量规则与人工抽检手册

## 1. 目的与适用范围

本手册用于运营专家对 Agent 生成的运营报告进行统一抽检。抽检负责判断专业深度和业务可用性，不替代系统的确定性检查，也不得在评分过程中直接改写原报告。

适用报告包括拉新增长、用户留存、活动运营和内容运营四类场景。正式报告、方向性草案和失败说明均可抽检，但只有不存在阻断项且达到评分门槛的报告可以通过上线验收。

## 2. 抽检前置材料

评审者应获得以下只读材料：

1. 已确认的运营简报及版本标识。
2. 结构化运营报告和交付状态。
3. 证据附录、来源链接、发布日期或未知标记、访问日期。
4. 确定性质量检查结果和专业审查结果。
5. 对应黄金场景及 `human_review_rubric.yaml` 评分表。

不得要求或记录个人身份信息、客户明细、账号密钥和公司机密原文。评分只使用汇总数据、匿名描述与公开证据。

## 3. 不可绕过的确定性规则

系统在人工抽检前运行以下七条硬规则。任一规则出现阻断项时，评审者不得通过报告：

| 规则码 | 检查内容 | 典型返工节点 |
| --- | --- | --- |
| `section_completeness` | 必填章节存在且不为空 | `assembly` |
| `reference_resolvability` | 主张、证据、策略、行动、实验和指标引用可解析 | `assembly` |
| `fact_citation_coverage` | 每项事实都有可访问、已核验且明确支持该主张的证据 | `research` |
| `action_closed_loop` | 核心策略具有目标、人群、动作、触点、负责人、资源、时间和验收闭环 | `plan` |
| `metric_definition` | 结果、过程、风险指标均有口径、公式、来源、周期和判断规则 | `plan` |
| `resource_constraints` | 预算、团队、渠道、内容产能和周期冲突已披露并取舍 | `plan` |
| `no_automated_execution` | 报告明确属于决策支持且禁止自动执行外部投放 | `assembly` |

人工评审发现硬规则漏检时，应新增阻断 finding，不得因为系统检查显示通过而忽略。

## 4. 七维人工评分方法

每个维度使用 1–5 分，必须填写评分依据和报告位置。具体锚点和权重以 [human_review_rubric.yaml](../backend/src/ops_agent/evaluation/data/human_review_rubric.yaml) 为准。

| 维度 | 核心判断 |
| --- | --- |
| 需求完整性 | 目标、用户、阶段、周期、资源、基线和限制是否完整且可追溯 |
| 证据质量 | 事实是否被证据支持，来源等级、时效、冲突和因果边界是否披露 |
| 场景适配性 | 案例是否结合当前资源、渠道、阶段和模式完成迁移，而非直接复制 |
| 策略逻辑 | 诊断、核心矛盾、策略机制、影响路径和替代解释是否闭环 |
| 执行可行性 | 阶段行动、负责人、依赖、资源、交付物、验收和降级方案是否可执行 |
| 指标可衡量性 | 三类指标与实验能否验证策略，是否避免无依据的虚假精确 |
| 风险覆盖 | 重大风险是否具有触发条件、监控指标、负责人、缓解与停止规则 |

评分纪律：

- 只能根据报告内容、用户确认输入和可访问证据评分，不得凭个人经验替报告补充缺失信息。
- 发现相关性冒充因果、单一案例泛化、资源冲突或虚假精确时，必须记录 finding。
- 每个 finding 必须指定唯一返工节点：`research`、`diagnosis`、`strategy`、`plan` 或 `assembly`。
- 阻断项描述应包含问题、报告位置、影响、返工节点和建议责任角色。
- 无法判断时应降低评分并说明所需补充材料，不能默认通过。

## 5. 操作步骤

1. 核对 `scenario_id`、`report_id`、简报版本和交付状态。
2. 检查确定性规则；存在阻断项时仍完成七维评分，但结论必须为不通过。
3. 按七个维度依次阅读报告，记录 1–5 分、具体依据和章节位置。
4. 将所有专业问题写入 `findings`；没有问题时保留空列表。
5. 使用 `score_human_review` 计算加权分、低于门槛的维度、阻断项和返工节点。
6. 复核结构化结果：七个维度不可缺失，时间必须含时区，finding ID 不得重复。
7. 保存原始评分与计算结果，不覆盖此前的评审版本。

通过条件同时满足：加权分不低于 4.0、所有维度达到各自门槛、没有阻断 finding。否则应根据返工节点修订并重新抽检。

## 6. 结构化结果格式

完整示例见 [human-review.example.yaml](examples/human-review.example.yaml)。核心字段如下：

- `review_id`：本次评审唯一标识。
- `scenario_id`、`report_id`：被评估场景和报告。
- `reviewer_role`：仅记录角色，不记录个人敏感信息。
- `reviewed_at`：含时区的评审时间。
- `dimension_scores`：七个维度的分数、依据和报告位置。
- `findings`：问题、是否阻断、位置、返工节点和责任角色。
- `overall_comment`：总体判断和下一步建议。

系统计算结果还包含 `weighted_score`、`passed`、`below_threshold_dimensions`、`blocking_finding_ids` 和 `required_revision_targets`。

## 7. 复核与争议处理

上线验收建议由两名运营评审者独立盲评。同一维度相差 2 分及以上时，应由第三名评审者复核证据与评分锚点；不得简单取平均掩盖分歧。争议结论、采用理由和最终责任人应随评审版本保存。
